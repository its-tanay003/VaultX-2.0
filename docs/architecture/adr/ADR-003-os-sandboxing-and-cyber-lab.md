# ADR-003: Multi-Platform OS Sandboxing Strategy and Cyber Lab Isolation

- **Status**: Proposed
- **Deciders**: Product Owner, Security & Architecture Team
- **Date**: 2026-10-02
- **Technical Story**: Task P0-T03 — Write and ratify ADR-002 to ADR-009.
- **Governs**: `crates/sandbox`, `crates/process-supervisor`, `security/sandbox-profiles`.

---

## Context and Problem Statement

VaultX 2.0 executes untrusted code generated by AI models and runs offensive cybersecurity tools against local targets. Invariant 3 dictates: *"Fail closed: if the policy engine, sandbox or audit log is unavailable, the action is refused. Never fall back to unsandboxed execution. No 'disable sandbox' escape hatch."*

Operating systems provide fundamentally different isolation primitives:
- Linux provides namespaces, cgroups, Landlock LSM, and seccomp-bpf.
- Windows provides Job Objects, AppContainer, and Virtualization-Based Security (VBS) / WSL2.
- macOS provides Endpoint Security and `sandbox-exec` (Seatbelt).
- Cybersecurity tools (Kali Linux suite) require Linux-native network utilities (raw sockets, packet crafting) that cannot execute natively on Windows without Linux emulation.

---

## Decision

We adopt a tiered, OS-specific sandboxing architecture:

1. **Linux Native Sandboxing (P0/Tier 1)**:
   - **Mechanism**: **Bubblewrap (`bwrap`) + Landlock LSM + seccomp-bpf filters**.
   - Unprivileged user namespaces isolate filesystem mounts (read-only root, ephemeral tmpfs for workspace).
   - Landlock restricts file hierarchy traversal at the kernel level.
   - Strict seccomp filters block raw socket creation, ptrace, and dangerous syscalls.
2. **Windows Sandboxing (P0/Tier 1)**:
   - **Local Software Development**: Native **Windows Job Objects** with restricted security tokens (disallowing process group escapes, enforcing memory/CPU quotas, and restricting network access).
   - **Cybersecurity / Linux Tooling**: **WSL2 / Docker Desktop isolation**. Cyber tools run inside ephemeral WSL2 distributions or Docker containers with virtualized network adapters.
3. **macOS Sandboxing (Post-MVP / Deferred to Phase 3)**:
   - macOS Seatbelt (`sandbox-exec`) integration is deferred to post-alpha. macOS builds in MVP will require containerized execution via Docker for Desktop.
4. **Kali Security Range (Cyber Lab)**:
   - Cyber tools run in ephemeral, isolated Docker containers or dedicated WSL2 Kali instances.
   - Network egress is strictly locked via firewall rules to the target CIDR envelope defined in the active `SecurityScope`.
   - **MicroVM Fallback**: If container escape test suites fail or kernel sharing is deemed unacceptable in enterprise penetration testing, evaluate Firecracker / Cloud-Hypervisor microVMs.

---

## Architectural Critique & Challenges

- **Challenge**: The proposed decision suggests using WSL2 for *all* Windows sandboxing. Relying exclusively on WSL2 for ordinary Windows software engineering (e.g., local PowerShell, C#, or Windows-native build tools) introduces severe filesystem performance penalties (cross-boundary 9P translation between Windows NTFS and WSL2 ext4) and breaks native Windows developer toolchains.
- **Resolution**: Split Windows sandboxing into two clear channels:
  1. *Windows Native Workflows*: Enforced via Windows Job Objects + Restricted Security Tokens (native speed on NTFS).
  2. *Offensive Cyber & Linux Workflows*: Routed into WSL2 / Docker Kali containers where raw socket manipulation and Linux binaries are mandatory.

---

## Alternatives Considered

- **Universal MicroVMs (Firecracker / QEMU) Everywhere**: Rejected for MVP. Boot latency (100–300ms) and virtualization overhead on developer laptops without nested virtualization enabled make it too heavyweight for simple build/lint tasks.
- **Pure Docker Daemon Everywhere**: Rejected for developer tasks. Requires root/administrator daemons running continuously, introduces Docker socket security risks (CWE-250), and fails on enterprise laptops where Docker Desktop licenses are restricted.
- **Raw OS Execution with Model Prompts**: Rejected. Violates Invariant 1 and Invariant 3.

---

## Consequences

### Positive
- Fast startup times (<15ms on Linux via Bubblewrap; <10ms on Windows via Job Objects).
- Fail-closed isolation: if the platform sandbox adapter cannot initialize, execution is refused immediately with `SANDBOX_UNAVAILABLE`.
- Kali cybersecurity tools remain strictly bounded within a virtual network.

### Negative
- Sandbox adapters require OS-specific native code in `crates/sandbox` (Landlock on Linux, Win32 APIs on Windows).
- Windows users running cyber tools must have WSL2 or Docker installed.

---

## Security Impact

Directly enforces **Invariant 3** (fail-closed sandboxing) and **Invariant 4** (network scope lock). Prevents compromised agent tools from altering host system files, reading SSH keys, or pivoting into unauthorized network subnets.

---

## Revisit Trigger

**Revisit when**:
1. Any container escape test in `security/attack-fixtures/` succeeds against the Docker/WSL2 boundary (triggers immediate escalation to microVMs).
2. Windows introduces unprivileged user namespaces or lightweight native containers in consumer Windows 11 builds.
3. Linux distributions without unprivileged user namespaces enabled by default require alternative setuid sandbox helpers.
