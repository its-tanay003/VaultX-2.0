# ADR-010: Schema Codegen and Protocol Governance

- **Status**: Proposed
- **Date**: 2026-10-02
- **Author**: Antigravity & Tanay
- **Deciders**: VaultX Core Architecture Team
- **Consulted**: Engineering Master Specification (§6, §7, §11, §12, §17, §19, §20), Developer API (Doc 16)
- **Informed**: All Contributors

---

## Context

VaultX 2.0 operates an agent-first desktop and CLI environment where an untrusted AI model proposes actions, but a Rust runtime holds sole authority. All communication between the untrusted agent orchestrator (TypeScript), the desktop UI (Tauri / React), the CLI (TypeScript / Node), and the security supervisor (Rust) occurs over typed Inter-Process Communication (IPC) and structured event streams.

If schema definitions diverge across languages:
1. An untrusted agent might submit malformed or maliciously expanded capability requests that bypass string checks.
2. The runtime might deserialize unexpected JSON fields, violating fail-closed security.
3. Errors could leak internal stack traces rather than structured machine-readable error codes.
4. Breaking changes could silently slip into minor releases without semantic version negotiation.

We require a single source of truth for all protocol data models, deterministic cross-language code generation, strict JSON Schema validation, and automated continuous integration checks that fail on stale generated code or undeclared breaking schema modifications.

---

## Decision

1. **Source of Truth**:
   - `packages/schemas/v1/*.json` using **JSON Schema Draft 2020-12**.
   - Strict constraints enforced on every entity:
     - `additionalProperties: false` everywhere.
     - Strict size limits (`maxLength`, `maxItems`, `minimum`, `maximum`).
     - Strong regex patterns for UUIDs (`^[0-9a-fA-F-]{36}$`) and SHA-256 hashes (`^[a-f0-9]{64}$`).
     - Canonical capability vocabulary locked to the 15 approved capabilities from `CONSISTENCY.md`.
     - Standard error codes locked to the 9 stable codes (`POLICY_DENIED`, `SCOPE_DENIED`, `SANDBOX_UNAVAILABLE`, `TOOL_NOT_FOUND`, `APPROVAL_REQUIRED`, `VERIFICATION_FAILED`, `RESOURCE_LIMIT`, `PROTOCOL_VIOLATION`, `INTERNAL_ERROR`).

2. **TypeScript Generation**:
   - Use `json-schema-to-typescript` via a dedicated bundling script (`packages/schemas/scripts/generate-ts.ts`).
   - Generates strict TypeScript interfaces into `packages/protocol/src/generated/types.ts`.
   - Bundles all definitions into a unified schema definition map to prevent duplicate type emission.
   - Runtime validation provided via `ajv` (Draft 2020-12) with `ajv-formats`.

3. **Rust Generation & Data Modeling**:
   - Strongly typed Rust data structures in `crates/runtime-core/src/protocol/generated.rs`.
   - Enforce `#[serde(deny_unknown_fields)]` across every struct to match `additionalProperties: false`.
   - Implement `Serialize` and `Deserialize` using `serde` and `serde_json`.

4. **Codegen Governance & Anti-Drift Checks**:
   - All generated code files are committed to Git with a standard header:
     ```text
     // AUTO-GENERATED BY VALUTX CODEGEN - DO NOT EDIT MANUALLY
     // SOURCE: packages/schemas/v1/
     ```
   - Developers never manually edit files in `generated/`.
   - `pnpm run codegen:check` re-runs generation in CI; if the committed file differs from the generated output, CI fails immediately.
   - Rust tests (`protocol_codegen_staleness.rs`) assert file existence, header compliance, and schema source parity.

5. **Breaking Change Detection**:
   - `packages/schemas/scripts/check-breaking.ts` compares the active schema against a frozen baseline snapshot (`packages/schemas/v1/.baseline/`).
   - CI rejects any changes in `v1` that:
     - Remove an existing property.
     - Add a `required` property to an existing object (breaks existing payload producers).
     - Remove an enum variant (e.g., removing a capability or error code).
     - Alter fundamental data types.
   - Any such change requires bumping the schema version (e.g. creating `packages/schemas/v2/`).

6. **Protocol Versioning & Negotiation**:
   - Wire messages are wrapped in `ProtocolEnvelope` carrying:
     - `protocol_version: "1.0.0"`
     - `message_id`: UUIDv4
     - `timestamp`: ISO-8601 UTC
     - `sender` and `recipient` identifiers
     - `message_type`
     - `payload`: Bounded entity payload
     - `negotiation`: Optional client-supported version list and server selection (`REQUEST`, `ACCEPTED`, `REJECTED`).

## Alternatives Considered

1. **Protocol Buffers / gRPC**:
   - *Pros*: Built-in binary efficiency, mature multi-language codegen (`protoc`, `prost`).
   - *Cons*: Opaque binary payloads hinder human auditing, debugging, and tamper-evident logging in JSON-based audit logs; browser webview (Tauri) and CLI require extra serialization layers; JSON Schema is standard for web services and OpenAPI.
   - *Verdict*: Rejected for core MVP wire format. JSON Schema provides human transparency and direct alignment with OpenAPI 3.1.

2. **Hand-Coded Types in Both Languages**:
   - *Pros*: No external generator scripts.
   - *Cons*: Guaranteed drift over sprints, subtle serialization mismatches, accidental schema expansion. Violates the Engineering Rule in `AGENTS.md` ("Schema-first: types come from packages/schemas via codegen. Never hand-edit generated code").
   - *Verdict*: Rejected.

3. **OpenAPI Generator CLI**:
   - *Pros*: Full-suite client/server generator.
   - *Cons*: Heavy Java dependency (`openapi-generator-cli`), bloated generated TypeScript files with unnecessary HTTP clients, complex templating.
   - *Verdict*: Rejected in favor of lightweight, native Node/TypeScript `json-schema-to-typescript` and idiomatic Rust serde structures.

---

## Consequences

### Positive
- Strict contract enforcement: Rust and TypeScript serialize and deserialize identical structures.
- Untrusted agent model cannot inject arbitrary JSON keys because `deny_unknown_fields` and `additionalProperties: false` reject them.
- Immediate CI failure on schema drift or unversioned breaking changes.
- Stable machine-readable error codes eliminate raw stack traces across boundaries.

### Negative
- Schema authors must run `pnpm run generate:ts` whenever schemas change.
- Adding fields to existing objects requires making them optional in `v1` to maintain backward compatibility, or initiating a `v2` migration.

---

## Security Impact

- **Mitigates CWE-20 (Improper Input Validation)**: Schemas enforce explicit limits on string length, array items, and value ranges.
- **Mitigates Parameter Tampering**: `additionalProperties: false` prevents prototype pollution and unexpected parameter smuggling.
- **Mitigates Privilege Escalation**: Capability taxonomy is strictly locked to canonical enums; non-canonical strings fail deserialization and schema validation before reaching the policy engine.
- **Auditable Error Boundaries**: Sanitized `ProtocolError` envelope prevents secret leakage or memory addresses from leaking in error payloads.

---

## Revisit Trigger

Revisit this decision when:
1. Benchmarking shows JSON serialization is a bottleneck for high-throughput streaming (e.g. streaming >1000 terminal output chunks per second), necessitating binary CBOR or Cap'n Proto for internal local IPC streams.
2. A second major version (`v2.0.0`) of the VaultX protocol is formally drafted.
3. Third-party external plugin SDKs require client code generation in languages other than Rust and TypeScript (e.g. Go or C).
